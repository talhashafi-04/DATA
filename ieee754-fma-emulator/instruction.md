/app/task-deps and /app/data/cases.json are provided as a starting point. The visible corpus is purposefully wide and "noisy": ordinary finite inputs, special values, exact-zero outputs, cancellation, overflow rescue, underflow, subnormal boundaries and fused-operation gaps. The fix needs to be a general solution to further probes of the same semantics.

Keep this entry point in place: double softfma(double a, double b, double c). The runner interface needs to work, too. The core arithmetic should be in software, and the implementation should be separate from long double __float128 and _Float128. These are fallback diagnostics in this image.

Any ordinary scalar arbitrary-precision computations can be performed using the existing libraries in the image. The implementation uses scalar computation for this operation; fused multiply-add primitives and whole-operation delegation to compiler or hardware FMA are prohibited. Keep quadmath, fma() fmaf() fmal(), __builtin_fma, __builtin_fmaf, __builtin_fmal, and helpers such as mpfr_fma away from /app/softfma.c. The core should compute from its arguments. Case files, reports, environment variables and other process state stay away from the answer path.

Results need to conform to round-to-nearest-even binary64, for the operation $a \times b + c$. This consists of finite values, NaN handling, infinities, signed zero results, exact cancellation, overflow, final subnormal values, and cases where rounding the multiply before adding would change the answer.

Expose double softfma_rounded(double a, double b, double c, int mode) from /app/softfma.c. It takes a, b, c and mode. The mode values are constant: 0 = round-to-nearest-even, 1 = round toward zero, 2 = round toward positive infinity, 3 = round toward negative infinity.

For NaNs, infinities, and invalid zero-times-infinity products, softfma_rounded returns the same value as softfma(a, b, c) for all modes.
